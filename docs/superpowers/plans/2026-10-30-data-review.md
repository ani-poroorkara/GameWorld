# Independent content/editor and world/puzzle review

Reviewed the completion contract, content/world reports, scoped source and tests, and the supplied temporary source snapshots. No implementation changes or broad test reruns. Executed small read-only Node probes for the findings below. Runtime integration was outside this review.

**Spec verdict: changes required. Quality verdict: changes required.** The fixed five puzzles and default geographic placements are credible; the remaining blockers concern the promised editable campaign rather than their basic playability.

1. **P1 — authored region bounds never control generation or region lookup.** `prototype/act1-world.js:5` computes regions from hardcoded radii; the definition merge at lines 41–43 omits regions; line 71 returns hardcoded bounds. Current exported forest bounds are x/y25–118 and cracked bounds5–138, whereas built forest is35–109 and cracked12–132. Probe: `Act1World.regionAt(30,60)` returns `cracked` although that point belongs to the authored forest. Saving region edits therefore changes export but cannot change this world API, tile classification, habitat selection or returned region bounds. Align the default metadata and use authored regions consistently in build/lookup (or explicitly reject unsupported edits instead of presenting them as effective).

2. **P2 — draft or removed default entities reappear physically.** `content/export.cjs:16` correctly excludes drafts, but `prototype/act1-world.js:22` onward installs default entities before the additive definition merge at lines 41–43. Probe: make `chest-apple` draft, export, build with that export: `exportHasChest=false`, `worldHasChest=true`. The same pattern applies to NPCs, puzzles and passages. Distinguish no-definition fallback generation from authoritative authored group lists, or reject disabling required fixed entities at export. A successfully exported approval decision should not silently leave the old world object present.

3. **P2 — puzzle authoring can export unsupported runtime sites and cannot edit the required puzzle parameters.** The editor creates new puzzle IDs (`editor/app.js:54`) and exposes kind/placement/requires/rewards only (`editor/app.js:74–75`). `editor/model.js:39` accepts any nonempty kind; `content/export.cjs:16` exports it; the world then installs the site. However `prototype/act1-puzzles.js:5–13` implements only five hardcoded IDs and hardcoded instructions/hints/solutions; `initial('custom-channels')` throws even when the editor-created approved channels puzzle exports successfully. Task 12 explicitly requires puzzle parameters. Provide a validated data-driven mechanic definition consumed by the puzzle API and editable clues/solutions, or constrain authoring to supported definitions and implement the promised parameter scope. At minimum reject unsupported approved puzzle IDs/kinds before runtime export. This is an unfinished scope visible in the supplied content/editor snapshot, not attributed solely to the latest delta.

4. **P2 — missing final quest stage validation remains absent.** `editor/model.js:41` only requires one stage and structurally valid stage fields. Removing the `dilemma` stage from the main quest produces zero validation errors and exports successfully, contrary to Task 12's explicit missing-final-stages validation requirement. Introduce an explicit terminal-stage contract and validate it for approved main quests; a generic editor need not hardcode narrative prose. This gap also predates the latest model delta in the supplied snapshot.

Positive checks: server save protections remain substantively unchanged from the snapshot (local host/origin checks, token, revisions, bounded UTF-8 body, serialized writes, atomic replacement and backups). The added export endpoint preserves token/origin protection. Saved embedded campaign wins over the seed in the exporter; approved numeric nulls and missing dice policies are rejected instead of coerced; script-like source text is escaped by replacing `<`, and editor dynamic text uses `esc`. Card-reference cycles and campaign prerequisite cycles are checked. Default NPC/chest/puzzle/passage positions agree between metadata and world; nine default passages exist, all thief placements use paths, and the tests meaningfully check connectivity with enemies treated as blockers. The five fixed puzzle APIs are pure, serializable, retryable and resettable, with explicit textual clues and independent solutions exercised by tests. No new persistence or source-injection blocker was found.

The existing reported test passes establish baseline module behavior; they do not exercise the authored-region/draft-removal/unsupported-puzzle and missing-terminal-stage cases above. No actual-browser or full-runtime assertion is made here.
